# 1. Цель переработки
Текущая таблица `DeveloperOffers` смешивает сразу несколько сущностей:
- застройщика;
- проект / ЖК;
- программу рассрочки;
- географические данные;
- ссылку на фид;
- объектовые данные из фида.
Для MVP лучше разделить эти сущности, чтобы:
1. Не дублировать застройщиков и проекты.
2. Корректно хранить фиды и объекты из фида.
3. Поддерживать фильтры по комнатам, типам недвижимости, цене и программам.
4. Подготовить основу для админки и импорта.
5. Сохранить простую структуру для API и поиска.
# 2. Общие требования к БД
## 2.1. СУБД
Используется:

```text
PostgreSQL 14+
```
## 2.2. Типы идентификаторов
Все основные сущности используют UUID:
```sql
UUID PRIMARY KEY DEFAULT gen_random_uuid()
```

## 2.3. Даты
Все даты храним в:
```sql
TIMESTAMPTZ
```
## 2.4. Деньги и проценты
Деньги:
```sql
NUMERIC(18,2)
```
Проценты:
```sql
SMALLINT -- для целых процентов, например ПВ
NUMERIC(5,2) -- для ставок, удорожания
```
## 2.5. Массивы и гибкие поля
Для массивов используем JSONB:

```sql
JSONB NOT NULL DEFAULT '[]'
```
Примеры:
```text
metro_stations
property_types
rooms_available
images
room_areas
payment_types
infrastructure
```
## 2.6. Удаление данных

Для MVP не используем физическое удаление важных бизнес-сущностей.
Вместо удаления применяем:

```sql
is_active BOOLEAN NOT NULL DEFAULT true
```
Исключение:
- технические связи;
- сессии;
- пользовательские события можно удалять по TTL-политике позже.

# 4. Логика связей

```text
developers
    ↓ 1:N
projects
    ↓ 1:N
offers
    ↓ N:M через offer_feeds
realty_feeds
    ↓ 1:N
feed_realty_objects
```

Пояснение:
- один застройщик может иметь много проектов;
- один проект может иметь несколько программ рассрочки;
- одна программа рассрочки может быть связана с одним или несколькими фидами;
- один фид содержит много объектов недвижимости;
- объекты фида не содержат финансовые условия рассрочки;
- финансовые условия хранятся в `offers`.

### Важные бизнес-правила для `offers`
#### 1. Цена для фильтров
Поле:
```text
price_min
```
считается **базовой ценой объекта** и используется для фильтрации.
Наценка не включается в `price_min`.
#### 2. Эффективная цена для калькулятора
Эффективная цена с наценкой рассчитывается отдельно:

```text
effective_price =
    price_min
    + price_min * price_markup_percent / 100
    + object_markup_fixed
```
#### 3. Беспроцентная рассрочка
Если:
```text
interest_rate_percent = 0
```
то
```text
is_interest_free = true
```
#### 4. Доступные комнаты

Поле:
```text
rooms_available
```
хранит коды:
```json
["studio", "1", "2", "3_plus"]
```
#### 5. Доступные типы недвижимости

Поле:
```text
property_types
```
хранит коды:
```json
["flat", "studio", "office", "retail"]
```

# 8. Важные MVP-допущения
## 8.1. Один проект может иметь несколько программ
Таблица `offers` позволяет хранить несколько программ рассрочки на один проект.
Пример:
```text
Проект: ЖК Amber City
Offer 1: Беспроцентная рассрочка 9 мес
Offer 2: Рассрочка для беременных
Offer 3: Рассрочка с переходом на ипотеку
```
## 8.2. Один фид может использоваться несколькими предложениями
Связь сделана через:
```text
offer_feeds
```
Это позволяет не дублировать фид, если одна выгрузка относится к нескольким программам.
## 8.3. Объекты фида не содержат условий рассрочки
Фид даёт только объектовые данные:
```text
цена
площадь
комнаты
адрес
метро
изображения
описание
```
Финансовые условия рассрочки хранятся в:
```text
offers
```
## 8.4. `price_min` — базовая цена для фильтров
Фильтры работают по:
```text
offers.price_min
```
Наценка учитывается отдельно:
```text
price_markup_percent
object_markup_fixed
```
## 8.5. `rooms_available` — агрегированное поле
Поле:
```text
offers.rooms_available
```
заполняется:
- вручную при импорте;
- автоматически из фида;
- агрегируется по объектам фида.
Коды:
```text
studio
1
2
3_plus
```

## 8.6. Избранное без регистрации

Для MVP избранное хранится по:
```text
user_sessions.id
```
Если позже появятся пользовательские аккаунты, нужно будет добавить:
```text
users
user_accounts
```
и связать избранное с пользователем.

# 11. Короткое описание архитектуры для разработчиков

```text
Пользователь открывает портал.
→ Создаётся user_sessions.
→ Пользователь выбирает целевую группу и бюджет.
→ Обновляется user_sessions.
→ Пользователь применяет фильтры.
→ Запись сохраняется в user_search_filters.
→ API читает offers_search + фильтры.
→ Пользователь видит карточки offers.
→ Просмотры пишутся в user_views.
→ Расчёты пишутся в user_calculations.
→ Конверсии пишутся в user_conversions.
→ Подписки пишутся в user_subscriptions.

Застройщик загружает выгрузку.
→ Создаются developers, projects, offers.
→ Если есть feed_url, создаётся realty_feeds.
→ Парсер сохраняет объекты в feed_realty_objects.
→ Агрегированные данные обновляют offers.rooms_available, offers.property_types, offers.price_min.
```
# 12. Что нужно подтвердить перед разработкой

## 1. Уровень сущности `offers`
Текущая логика:
```text
offers = программа рассрочки / предложение застройщика
```
Не квартира и не отдельный объект из фида.
## 2. Цена для фильтров
Текущая логика:
```text
Фильтры используют базовую price_min без наценки.
```
Наценка используется в калькуляторе и карточке.
## 3. Избранное
Текущая логика:
```text
Избранное хранится по session_id без регистрации.
```
