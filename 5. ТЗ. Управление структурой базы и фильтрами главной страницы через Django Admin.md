## 1. Назначение документа

Документ описывает требования к административной панели на базе **Django Admin** для управления:

1. структурой данных базы застройщиков;
2. маппингом полей выгрузки застройщика;
3. основными фильтрами главной страницы;
4. дополнительными фильтрами главной страницы;
5. условиями отображения фильтров в зависимости от целевой группы, устройства, активности предложений и других параметров;
6. справочниками, опциями фильтров и правилами их вывода.
Решение должно позволить контент-менеджеру или администратору портала без участия разработчика:
- добавлять новые фильтры;
- редактировать существующие фильтры;
- отключать фильтры;
- менять порядок отображения;
- задавать, является ли фильтр основным или дополнительным;
- привязывать фильтр к полю из базы застройщиков;
- управлять опциями фильтра;
- просматривать историю изменений.

## 3. Основная идея
Главная страница портала формирует набор фильтров не жёстко в коде, а на основе данных из базы застройщиков и настроек в Django Admin.
То есть:
- администратор управляет справочником полей и фильтров;
- каждый фильтр привязан к определённому полю или вычисляемому признаку;
- фронтенд получает список фильтров через API;
- отображение фильтров зависит от настроек, целевой группы и наличия данных.
Пример:

```text
Поле в базе застройщиков: is_it_mortgage
Название фильтра: IT-ипотека
Тип виджета: чекбокс
Целевые группы: все
Размещение: дополнительные фильтры
Состояние: активно
```

После сохранения в Django Admin фильтр появляется на главной странице без необходимости менять код фронтенда.
## 4. Термины

| Термин | Описание |
| --- | --- |
| База застройщиков | Таблица `DeveloperOffers`, содержащая предложения застройщиков и условия рассрочек |
| Маппинг | Соответствие между полями выгрузки застройщика и полями базы данных |
| Фильтр | Элемент интерфейса, позволяющий пользователю сузить выдачу |
| Основной фильтр | Фильтр, отображаемый на главной странице по умолчанию |
| Дополнительный фильтр | Фильтр, доступный в блоке «Дополнительные фильтры» или «Ещё» |
| Группа фильтров | Логическая группировка фильтров: финансы, программы, география, инфраструктура и т.д. |
| Виджет | Тип UI-элемента: чекбокс, слайдер, выпадающий список, мультиселект и т.д. |
| Условие отображения | Правило, при котором фильтр показывается или скрывается |
| Django Admin | Административная панель Django |
| Целевая группа | Сегмент пользователя: молодая семья, инвестор, индивидуальный покупатель |

## 5. Роли и права доступа
### 5.1. Суперадминистратор
Имеет полный доступ:
- управление пользователями;
- управление ролями;
- управление структурой полей;
- управление фильтрами;
- управление маппингом;
- просмотр аудита;
- изменение системных параметров.
### 5.2. Контент-менеджер
Может:
- добавлять и редактировать фильтры;
- менять порядок отображения;
- отключать фильтры;
- редактировать названия и описания;
- управлять опциями фильтров;
- просматривать историю изменений.
Не может:
- удалять системные поля;
- менять технический код поля;
- изменять структуру базы данных на физическом уровне;
- менять настройки интеграций.
### 5.3. Аналитик
Может:
- просматривать справочники;
- просматривать статистику использования фильтров;
- выгружать данные;
- просматривать журнал действий.
Не может редактировать фильтры.

## 6. Управление структурой базы данных

Под управлением структурой базы данных в рамках данного ТЗ понимается не прямой `ALTER TABLE` через админку, а управление справочником полей, маппингом и отображением.
Физическое изменение структуры базы данных выполняется через миграции разработчиками.
Для гибких полей  использовать JSONB-поле:

```sql
extra_attributes JSONB
```

## 9. Логика отображения фильтров на главной странице

Главная страница должна динамически собирать фильтры на основе настроек из Django Admin.

### 9.1. Входные параметры

При загрузке главной страницы система учитывает:

```text
1. Выбрана ли целевая группа.
2. Если выбрана, какая именно: family, investor, individual.
3. Тип устройства: desktop, mobile, tablet.
4. Есть ли активные предложения в базе.
5. Какие фильтры активны.
6. Какие фильтры являются основными.
7. Какие фильтры являются дополнительными.
8. Какие условия отображения указаны в visibility_conditions.
```

## 9.2. Алгоритм получения фильтров

```text
1. Пользователь открывает главную страницу.
2. Фронтенд запрашивает список фильтров у API.
3. API определяет target_group пользователя.
4. API выбирает активные FilterItem.
5. API фильтрует их по target_group.
6. API применяет placement: main / additional.
7. API проверяет visibility_conditions.
8. API считает количество доступных предложений для фильтра.
9. Если hide_if_no_offers = true и предложений нет, фильтр скрывается.
10. API возвращает список групп и фильтров с сортировкой.
```

## 10. Условия отображения фильтров
Каждый фильтр может иметь набор условий отображения.
### 10.1. Описание условий

| Условие | Описание |
| --- | --- |
| `target_groups` | Показывать фильтр только для перечисленных целевых групп |
| `device` | Показывать только на определённых устройствах |
| `min_active_offers` | Минимальное количество активных предложений, при котором фильтр показывается |
| `hide_if_no_offers` | Скрывать фильтр, если по нему нет предложений |
| `feature_flag` | Показывать только при включённом feature flag |
| `require_target_group` | Показывать только после выбора целевой группы |
| `show_only_if_field_has_data` | Показывать, если поле заполнено хотя бы у части активных предложений |
### 10.2. Логика применения

Все условия внутри `visibility_conditions` применяются по принципу `AND`.

## 12. Примеры фильтров и их настроек

## 12.1. Фильтр «Бюджет»

```yaml
code: budget
title: Ваш бюджет
group: basic
offer_field: session_budget_total
widget_type: slider
placement: main
api_param: budget
operator: less_or_equal
target_groups: all
is_active: true
settings:
  min: 5000000
  max: 100000000
  step: 500000
  currency: RUB
```

## 15. Логика добавления нового фильтра

### Сценарий: администратор хочет добавить фильтр «IT-ипотека»

Шаги:

```text
1. Открыть Django Admin.
2. Перейти в раздел «Поля базы застройщиков».
3. Найти поле is_it_mortgage.
4. Проверить, что поле активно и доступно для фильтрации.
5. Перейти в раздел «Фильтры главной страницы».
6. Нажать «Добавить фильтр».
7. Указать:
   - Название: IT-ипотека
   - Код: it_mortgage
   - Группа: Программы
   - Поле базы: is_it_mortgage
   - API-параметр: is_it_mortgage
   - Оператор: equals
   - Тип виджета: checkbox
   - Размещение: additional
   - Целевые группы: все
8. Указать условия отображения:
   - скрывать, если нет предложений;
   - минимальное количество предложений: 1.
9. Сохранить.
10. Проверить фильтр на превью главной страницы.
```

После сохранения фильтр должен быть доступен на фронтенде.

Удаление фильтра должно быть безопасным.

### Рекомендуемая модель

Вместо физического удаления использовать статусы:

```text

```

### Правила


Это необходимо для:

```text

3. Персонализации.
4. A/B-тестов.
5. Улучшения главной страницы.
```
## 23. Валидация и защита от ошибок

### 23.1. Обязательные проверки

```text
1. У фильтра должен быть уникальный code.
2. У фильтра должен быть уникальный api_param.
3. Фильтр должен быть привязан к полю или вычисляемому источнику.
4. Для select/multiselect должна быть минимум одна активная опция.
5. Для boolean-фильтра опции не требуются.
6. Для range-фильтра должны быть указаны min и max.
7. Целевая группа должна быть указана или выбран режим «все группы».
8. Поле, к которому привязан фильтр, должно быть активно.
```

### 23.2. Предупреждения

```text
1. Фильтр не имеет предложений.
2. Фильтр является основным, но по нему мало данных.
3. Для целевой группы слишком много основных фильтров.
4. Поле базы не заполнено ни у одного активного предложения.
5. Фильтр дублирует другой фильтр по смыслу.
```

## 28. Ошибки и граничные случаи

### 28.1. Поле не найдено

Если фильтр привязан к полю, которого нет в `DeveloperOffers` или `OfferField`, админка должна показать ошибку:

```text
Выбранное поле базы недоступно. Проверьте маппинг или деактивируйте фильтр.
```

### 28.2. Нет предложений

Если активные предложения отсутствуют, фронтенд должен скрыть фильтр при:

```text
hide_if_no_offers = true
```

### 28.3. Конфликт API-параметров

Если два фильтра используют один `api_param`, сохранение должно быть запрещено:

```text
Другой фильтр уже использует этот API-параметр. Укажите уникальное значение.
```

### 28.4. Несоответствие типа данных

Если boolean-фильтр привязан к текстовому полю, показать предупреждение:

```text
Тип поля базы не соответствует типу фильтра. Проверьте маппинг.
```

## 29. Acceptance criteria

### 29.1. Управление фильтрами

```text
1. Администратор может создать новый фильтр через Django Admin.
2. Администратор может отредактировать фильтр.
3. Администратор может деактивировать фильтр.
4. Администратор может изменить порядок фильтров.
5. Администратор может выбрать, является ли фильтр основным или дополнительным.
6. Администратор может привязать фильтр к полю базы застройщиков.
7. Администратор может задать целевые группы.
8. Администратор может добавить опции фильтра.
```

### 29.2. Отображение на главной странице

```text
1. Активные фильтры появляются на главной странице без деплоя.
2. Деактивированные фильтры не отображаются.
3. Основные фильтры отображаются в основном блоке.
4. Дополнительные фильтры отображаются в блоке дополнительных фильтров.
5. Фильтры отображаются согласно сортировке.
6. Фильтры отображаются только для подходящих целевых групп.
7. Фильтры скрываются, если по ним нет активных предложений и включено hide_if_no_offers.
```

### 29.3. Маппинг

```text
1. Каждый фильтр привязан к полю, API-параметру или вычисляемому источнику.
2. Система не позволяет создать фильтр без источника данных.
3. Система не позволяет использовать один API-параметр в двух фильтрах.
4. Изменение маппинга отражается на фильтрации.
```

### 29.4. Аудит

```text
1. Все изменения фильтров логируются.
2. Можно посмотреть, кто и когда изменил фильтр.
3. Можно посмотреть старое и новое значение.
```
